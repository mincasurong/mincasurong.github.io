Dissecting m9g-agent-corps: Why Production Coding Harnesses Outperform Custom Multi-Agent Wrappers — and What Antigravity (agy) Actually Is

When building our own 3-tier multi-agent coding corps (m9g-agent-corps / m9g-code, 31 Python modules in src/ag_harness/), two core architectural questions emerged: (1) Why does our LLM calling and multi-agent harness still feel noticeably more brittle under real engineering load than OmO (Oh-My-OpenAgent), Claude Code, Codex, Grok Bot, or native Antigravity (agy)? And (2) Is Antigravity (agy) fundamentally a containerized/lightweight Gemini worker meant to be called from outer agents, or a full subagent coding harness? 1. Auditing the Debate: Your Intuition vs. The Other Agent's Verdict

During development of m9g-agent-corps, we posed a candid engineering question: Why does our custom multi-agent harness feel worse than existing systems like agy, omo, grok bot, codex, and Claude Code? And isn't Antigravity (agy) essentially a dockered lightweight Gemini agent callable as a worker from other agents rather than a subagent-spawning harness like Claude Code? Another agent responded with the following claim:

Other Agent's Claim (Under Audit):
"Your m9g-agent-corps 3-tier design (HQ orchestrator + isolated workers returning short handoffs) is sound and already uses the Antigravity SDK for the actual agent loop, so the core model calling is not reinvented from scratch; it feels worse than agy, Claude Code, OmO, or Codex mainly because those systems have far more mature reliability layers (tool-call recovery, strict context isolation, independent verification gates, model-specific co-optimization, and observability) that reduce partial failures and context noise under real load. Antigravity itself is a full coding harness with custom/dynamic subagents, parallel worktrees, /boost and teamwork modes, and a Manager view—not merely a lightweight Gemini worker you call from elsewhere—though composing it that way (as you and others do) is a valid pattern."

By inspecting the actual source code in D:/git/m9g-agent-corps/m9g-agent-corps/src/ag_harness/ alongside Google's official Gemini Interactions API documentation, we can separate what is verified fact from what the other agent oversimplified:

Where Your Intuition Is 100% Spot-On

Surface 1: Antigravity as a Sandboxed Linux Worker Container

In Google's Gemini Interactions API (client.interactions.create(agent="antigravity-preview-09-2026", environment="remote")), Antigravity literally runs inside a Google-managed sandboxed Linux container with Bash, Python, Node.js, file I/O, and web access—built specifically to be called as an autonomous remote worker! Furthermore, when called via CLI pipe mode (agy -p <prompt> --model gemini-3.8-flash --mode auto in agy_workers.py:195-214) from OmO, Claude Code, or Codex, it operates as a stateless, skill-loaded leaf execution worker.

Where the Other Agent Was Right (& What It Missed)

Surface 2: Interactive Harness vs. Orchestrator-on-Orchestrator

The other agent is correct that agy as a standalone product includes a Manager view, /boost, worktrees, and custom agents (client.agents.create()), and that m9g-agent-corps imports from google.antigravity import Agent (agy_workers.py:21). What it missed: when an outer harness (OmO, Claude Code, or m9g) calls agy as a subagent, you must suppress nested subagent spawning—otherwise stacking an orchestrator inside an orchestrator creates an O(bd) branching explosion and double-summarization loss!

2. Inside m9g-agent-corps: The 3-Tier Architecture

Before diagnosing its failure modes, let us examine what m9g-agent-corps gets right. Across 31 modules in src/ag_harness/, the system implements a Commander -> Executive Orchestrator -> Isolated Corps Units hierarchy designed to keep the frontier model's context window clean and preserve Gemini's 95% implicit cache discount ($2.00/1M uncached vs. $0.10/1M cached input tokens in corps.jsonc):

Figure 1. Architectural schematic of m9g-agent-corps (generated via our custom nanobanana-architecture skill on gemini-3-pro-image): Left — Tier 1 Executive Orchestrator (gemini-4-argon / APEX) with 2-tier skill disclosure and AST skeletonization; Center — Tier 2 (MIDDLE) and Tier 3 (WORKHORSE / SCOUT) workers running on google.antigravity.Agent or agy/omo CLI subprocesses; Right — the 6 concrete reliability gaps compared against production harnesses.
  • Tier 1 — APEX Executive Orchestrator (config.py:258): Runs gemini-4-argon / gemini-2.5-pro with a 150,000-token ceiling and ThinkingLevel.HIGH. It places [SYSTEM_ROLE: ...] and the 1-line-per-skill <global_skill_catalog> at the exact start of system_instructions so the prefix remains immutable across turns for implicit caching.
  • Tier 2 — MIDDLE Pro Implementer (subagents.py:139): Runs gemini-2.5-pro with a 180,000-token ceiling guarded by trim_context_for_tier2() to prevent crossing the 200k-token pricing cliff.
  • Tier 3 — WORKHORSE & SCOUT (agy_workers.py:118, subagents.py:105): Routes via select_subagent_harness() to either agy (for tasks with attached skills or matching 28 domain keywords in AGY_DOMAIN_KEYWORDS such as isaac, ros2, cuopt, rea, gcloud) or single-agent omo (for surgical code edits) on gemini-3.8-flash / gemini-3.5-flash-lite.

3. Why m9g-agent-corps Feels Worse Than OmO, Claude Code, and Codex: 6 Code-Verified Bottlenecks

Even though m9g-agent-corps uses the official google.antigravity.Agent loop and CLI subagents, inspecting src/ag_harness/ reveals six concrete engineering bottlenecks where information is lost, errors are masked, or latency is multiplied compared to mature harnesses like OmO, Claude Code, and Codex:

Bottleneck 1 — Silent False-Positive SUCCESS in Regex Handoff Parsing (agy_workers.py:296-305)

In WorkerHandoffReport.parse_from_markdown(), the orchestrator does not receive structured tool-execution state from the worker. Instead, it asks the worker to print a Markdown block at the end of its reply and parses it with regular expressions:

# src/ag_harness/agy_workers.py (Lines 298-299)
status_match = re.search(r"## STATUS:\s*([A-Z_]+)", raw_text)
status = status_match.group(1) if status_match else "SUCCESS"

Why this hurts reliability: Whenever a worker hits its token limit, gets cut off mid-stream, crashes inside a CLI subprocess with non-zero exit code (check=False at line 415!), or simply omits the exact ## STATUS: heading, parse_from_markdown() defaults status to "SUCCESS" with files_modified=[]. The Higher Brain believes the subtask succeeded and moves on, compounding silent partial failures across waves.

Bottleneck 2 — Blocking 300-Second Black-Box CLI Subprocesses (agy_workers.py:409-424)

When M9G_SUBAGENT_BACKEND dispatches a worker to agy.exe -p or omo.exe -p, it wraps a synchronous blocking subprocess.run inside asyncio.to_thread:

# src/ag_harness/agy_workers.py (Lines 409-417)
proc = await asyncio.to_thread(
  subprocess.run, cmd, cwd=abs_ws, capture_output=True, text=True, timeout=300, check=False
)

Why this feels stuck vs. OmO & Claude Code: Because capture_output=True buffers stdout/stderr until process exit, the Higher Brain has zero live visibility while the child runs (up to 5 minutes). You cannot peek at partial progress (like OmO's task_output(mode="tail")), you cannot steer a drifting worker mid-turn (like OmO's task_send), and if the child hits the 300s timeout, subprocess.TimeoutExpired discards the buffered work and returns an empty failure report.

Bottleneck 3 — Mandatory Delegation Tax ("Rule 1") & 19-Tool Prompt Bloat (config.py:345-485)

In config.py:457, the Higher Brain system prompt enforces Rule 1 (Stay Above the Weeds): "you MUST NOT read 500-line files directly into your own context. Instead... dispatch spawn_agy_worker." At the same time, _resolve_agent_tools() attaches 19 Higher-Brain tools plus up to 28,000 characters of static prompt prefix on Turn 1.

The Latency & Context Loss Penalty: For routine 1-to-3 file bug fixes, Claude Code, Codex, and OmO read the file, apply a surgical edit, and run diagnostics in a single in-process loop (~10–20 seconds). In m9g-agent-corps, Rule 1 forces a multi-hop relay: Higher Brain (Argon) -> cold-start Worker -> re-read files from disk -> compress to 300-word Markdown summary -> Higher Brain. That 300-word bottleneck strips subtle cross-file type invariants and doubles wall-clock latency.

Bottleneck 4 — Destructive Middle-Out String Slicing (hooks.py:686 & subagents.py:34)

To prevent TPM exhaustion, cap_tool_output() truncates every tool output exceeding 12,000 characters by keeping the first 4,000 characters and the last 8,000 characters, while trim_context_for_tier2() slices the middle out of file_context:

# src/ag_harness/hooks.py (Lines 23-25) & subagents.py (Lines 35-40)
DEFAULT_MAX_TOOL_CHARS = 12000  # HEAD_CHARS = 4000, TAIL_CHARS = 8000
file_context[:keep_chars // 2] + "\n...[TRIMMED]...\n" + file_context[-(keep_chars // 2):]

Why this causes blind retries: When reading a 600-line source file or a pytest log with 15 failures, lines 120–380 sit squarely in the deleted middle. The model never sees the failing assertion or helper definition in the middle of the file, leading to hallucinated edits or repeated tool calls. Production harnesses instead use line-indexed pagination (offset / limit) and structural compaction so the model explicitly pages through regions it needs.

Bottleneck 5 — Hard-Kill Loop Breaker Instead of Self-Healing Remediation (agy_workers.py:557)

When StreamLoopMonitor detects 3 identical tool calls or >2 status polls, _run_worker() and stream_turn() immediately break out of the response stream and terminate the turn with STATUS: FAILED. By contrast, production harnesses like OmO (via its TTSR stream-rule engine) and Claude Code inject a targeted in-session corrective interrupt (<system-interrupt> or tool-error feedback) that tells the model why its action was blocked so it can pivot to an alternative tool in the very next step without losing its working state.

Bottleneck 6 — Unwired Verification Substrate (argon_omo_substrate.py vs. agy_workers.py)

Ironically, m9g-agent-corps already contains sophisticated verification modules—IntentGate (blocking mutating tools until prove_plan() is called), HashlineEditor (SHA-1 line-hash anchored edits), and WorkspaceCheckpointManager (temporary GIT_INDEX_FILE tree snapshots for instant rollback). However, inside spawn_agy_worker() (agy_workers.py:536-588), none of those gates are enforced on the worker's output: the worker is merely asked in prose to fill out ### Verification Output:, whereas OmO and Claude Code enforce real diagnostics/test verification before a task can be marked complete.

5. Concrete Upgrade Blueprint for m9g-agent-corps

The takeaway from our audit is encouraging: you do not need to discard m9g-agent-corps's 3-tier architecture or stop calling agy as a specialized worker from OmO, Claude Code, or Codex. Instead, closing these four engineering gaps brings m9g-agent-corps to production-harness parity:

  1. Fix the False-Positive Handoff Bug (agy_workers.py:298) & Use Structured JSON Schema: Change the fallback in WorkerHandoffReport.parse_from_markdown() from "SUCCESS" to "FAILED" when status_match is None or proc.returncode != 0, and pass response_schema=WorkerHandoffReport directly to the Gemini call so handoffs are machine-typed rather than regex-scraped.
  2. Replace Blocking subprocess.run with Streaming Async Subprocesses (asyncio.create_subprocess_exec): Stream stdout/stderr lines incrementally through StreamLoopMonitor and expose a mid-turn steering pipe so workers are never 300-second black boxes.
  3. Relax "Rule 1" for <=3-File Edits & Wire HashlineEditor + WorkspaceCheckpointManager into Workers: Allow the orchestrator to edit 1–3 files directly via hashline_edit(), and when spawning workers, wrap each worker in a WorkspaceCheckpointManager snapshot that automatically runs pytest / syntax verification before accepting the worker's changes.
  4. Keep agy -p as a Single-Loop Leaf Worker When Called from Outer Harnesses: Continue passing --mode auto with delegation disabled (depth >= max_depth) whenever invoking agy from OmO, Claude Code, or m9g-agent-corps—leveraging Antigravity's rich domain skills and sandboxed execution without paying the orchestrator-on-orchestrator tax.
